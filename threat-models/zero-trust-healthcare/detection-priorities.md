# Contoso Regional Health (fictional): detection priorities

> **Reference work.** Fictional scenario built for a public portfolio. Not deployed in, derived from, or describing any employer environment. Not professional advice.

This is the detection backlog, in three priority tiers, for the companion detection pack (`coverage-map.md` and `detections-index.md`), derived directly from the attack paths in `attack-paths.md` and the trust-boundary analysis in `threat-model.md`. Each item is concrete: the behavior to detect, the MITRE ATT&CK technique it covers, the data source a detection would query, why it sits in its tier, and which attack path it serves. The intent is that each item becomes one or more rules (Defender XDR advanced hunting, Sentinel analytics, or Sigma) with the architecture components as context. Every detection rule named in this document is an untested template as of 2026-10-04 (`coverage-map.md` section 1).

Technique references use MITRE ATT&CK Enterprise v19.2, verified against MITRE's official ATT&CK STIX data. Data sources are named for the scenario stack: Microsoft Defender XDR advanced hunting tables, Microsoft Sentinel tables (including `SigninLogs`, `AADNonInteractiveUserSignInLogs`, `AuditLogs`, `OfficeActivity`, `SecurityEvent`), Microsoft Defender for Identity and Defender for Cloud Apps signals, and the network, EHR, and device logs that `PIP-SIEM` ingests under assumption A-17.

## How the tiers are set

An item's tier reflects three things together: how much of the top attack paths the detection covers, how reliably the behavior is observable in the available telemetry, and how close the behavior sits to irreversible harm (patient-safety or ePHI loss). P1 items are the ones to build first. Item numbers are stable identifiers that other files cite, not ranks.

## Response and clinical-safety constraint (read before wiring automation)

Response actions attached to these detections must respect the architecture's clinical safety gate and automation boundaries (ADR-008, `04-segmentation.md` section 3):

- Automated containment is allowed for devices that are not medical devices. A medical device in active patient use is never disconnected automatically; containment narrows to the anomalous flow and a clinical lead decides on a device swap. Automatic attack disruption excludes the medical device segments' address ranges from IP containment for the same reason (ADR-008).
- Automated identity response (session revocation, account disable) for high-confidence incidents must include a clinical notification step so unit leadership can move affected staff onto downtime procedures.
- Enforcement-linked detections in clinical and device zones run in report-only or monitor mode first (design principle P-6).

**Notes to the Priority 2 table.**

- **Item 9.** In the documented case the server was not onboarded to Defender for Endpoint. The design does not yet state Defender for Endpoint on the `IDS-SYNC` servers (`threat-model.md` TM-A4 and section 9 item 8). Until it does, the process half of this item has no data and the item rests on the Defender for Identity sensors' alerts and AuditLogs. Count the documented gap as closed only where Defender for Endpoint coverage of the sync servers is confirmed.
- **Item 10.** The roles to watch are the Tier 0 roles in `03-identity-and-access.md` section 4, which include Privileged Authentication Administrator, Security Administrator, Domain Name Administrator, and Application Administrator and Cloud Application Administrator at tenant scope, plus the roles 03 section 4 says are never assigned (Partner Tier1 Support, Partner Tier2 Support, Windows 365 Administrator, and External Identity Provider Administrator), so any assignment of one has no planned form. An Application Administrator assignment scoped to one application is Tier 1 only when that application is not Tier 0, so the rule has to tell tenant scope from application scope, or alert on both and close application-scoped results against their records.
- **Item 11.** A grant of any permission in `03-identity-and-access.md` section 6's table makes an application a Tier 0 workload identity, so every such grant belongs in the High branch, not only the authentication-method permissions. A credential added to a Tier 0 workload identity outlives the activation or run that added it, and nothing gates its later use (RR-16), so it alerts at High whoever adds it (03 section 4). Managed identities are outside CA-22, so their sign-ins need monitoring instead; managed identity sign-in monitoring is not built (`coverage-map.md` section 3, item 11).
- **Item 19.** Where no approval applies, the alert is the only control (RR-16): an emergency account changing the group or the other account, a Tier 0 workload identity granted RoleManagement.ReadWrite.Directory changing the group, and a Tier 0 workload identity that can issue a Temporary Access Pass issuing one to an emergency account. Benign results should be rare (announced validations, declared emergencies), so every result can alert at Tier 0 priority, as ADR-004 decision 9 requires. Credential changes on other Tier 0 accounts are outside this item. An administrator needs an approved Tier 0 activation first, which item 10's rule (SN-02) alerts on, its Tier 0 role list including Privileged Authentication Administrator; the change itself then shows only in AuditLogs, which SN-02's response notes have the responder review when no ticket explains the activation. An application needs no activation, so SN-02 does not see a pass it issues on another Tier 0 account. The design accepts that because such a pass yields less (`03-identity-and-access.md` section 4), and the grant of the permission, or a credential added to an application that holds it, alerts through SN-03 (item 11). SN-07 (the group and the account audit activity) and SN-06 (sign-ins) implement this item; `purple-team-plan.md` PX-19 and PX-20 validate them.
- **Item 20.** Removing an admin account therefore takes it out of those policies without editing one: the same exemption move as AP-5 step 8a, mapped the same way. Deleting a group makes the same move for every member at once. An owner added to a group can make that removal later with no Tier 0 activation, because owners of a role-assignable group can manage its membership (`03-identity-and-access.md` section 5): the durable form of the move, mapped to T1098.003 as in step 8a. A role assigned to a group would reach every member, which is step 8's move (T1098.003) made through the group. They are role-assignable groups with no owners and no role, so a change needs Tier 0 access, and the design requires a Tier 0 priority alert on every change, matched by object ID, with no exclusion for planned work (`03-identity-and-access.md` sections 3 and 4). Where no approval applies (an emergency account, or a Tier 0 workload identity granted RoleManagement.ReadWrite.Directory), the alert is the only control (RR-16). Benign volume follows administrator joiners and leavers, each under a change record. Activation is not affected, because CA-06 targets all users. SN-07 implements this item, and `purple-team-plan.md` PX-17 has a run for it.

## Coverage notes for detection engineering

- **Where prevention already holds, detect for assurance, not as the only control.** Items 12 and 13 largely confirm that `PEP-HOST` and tamper protection are working; alert volume should be low if they are.
- **Where prevention has a gap, detection is the compensation.** Items 3, 4, 5, and 11 cover behaviors the architecture cannot fully prevent (help-desk proofing, token theft on non-CAE apps, OAuth consent). These deserve the most tuning effort. Item 19 is the same case with almost no tuning to do: no approval gates the emergency accounts or Tier 0 workload identities (RR-16), so its alerts are the control there, and benign volume should be close to zero. Item 20 follows the same pattern for the admin groups, with benign volume set by administrator joiners and leavers.
- **Correlation beats single signals for the fraud path.** Item 3 plus item 4 plus a banking-change event is the AP-2 story; a single-signal rule on any one of them will be noisy, but the chain is specific. Recovery of diverted funds depends on speed, so this correlation should be near-real-time.
- **The local clinical plane is the blind spot (RR-02).** On-site EHR sign-ins carry no Conditional Access risk evaluation, so items 6, 7, 8, and 18 (Defender for Identity on the full Tier 0 set) carry more of the detection load there than they would on the cloud plane.
- **Map to the deliverables.** These items are the input to the detection pack's `coverage-map.md` (technique, data source, rule file, status, linked attack path) and `detections-index.md`. The attack-path IDs in the last column are the link back.
