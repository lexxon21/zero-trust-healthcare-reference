# Contoso Regional Health (fictional): HIPAA audit evidence map

> **Reference work.** Fictional scenario built for a public portfolio. Not deployed in, derived from, or describing any employer environment. Not professional advice.

For each of the 65 HIPAA Security Rule standards and implementation specifications in [crosswalk.yaml][cwyaml] (45 CFR 164.308 to 164.316), this map shows what HHS Office for Civil Rights (OCR) asks for under its published HIPAA Audit Protocol, and where the Contoso Regional Health (fictional) reference design would produce that evidence. Rows carry the same citations and XW identifiers as the crosswalk, so the two files line up row for row.

Status as of 2026-10-20.

## 1. Purpose and limits

- **Nothing is deployed, so no evidence exists.** This map shows only where evidence would come from if the design were built. Every detection rule is an untested template, neither incident response playbook has been exercised, the tabletop kit has not been run, and recovery is specified as requirements only (RR-11).
- **Not an audit.** It is not an audit, an assessment, an attestation, or an evaluation under 45 CFR 164.308(a)(8). It predicts no audit outcome and certifies nothing about any organization.
- **Sources.** The "what the auditor asks" column comes only from OCR's public audit protocol, paraphrased, with brief quotations; the protocol is a US government work. A few rows add a NIST SP 800-66 Rev. 2 key activity, labeled as NIST guidance, not as an OCR inquiry. The "where" column comes only from this repository's fictional design: the architecture documents and ADRs, the detection pack, the crosswalk, the notification clock matrix, the risk register, and the executive risk brief. The map adds no evidence request list, sampling approach, document naming, or commentary beyond what the protocol itself says.
- **Which protocol.** OCR's page headed "Audit Protocol" is marked "Updated July 2018", and its footer reads "Content last reviewed February 3, 2025". It still describes itself in terms of "The Phase 2 HIPAA Audit Program". The page states that "The audits performed assess entity compliance with selected requirements and may vary based on the type of covered entity or business associate selected for review." hhs.gov returned HTTP 403 to automated retrieval on 2026-10-20, so the text was read from Archive-It captures of the page dated 2025-09-13 and 2026-08-22 (Sources).
- **Current audits.** OCR's audit program page says its 2024-2025 audits "will review 50 covered entities' and business associates' compliance with selected provisions of the HIPAA Security Rule most relevant to hacking and ransomware attacks", and links the protocol as "the full Audit Program Protocol". OCR has not said which protocol rows those audits use. This map therefore cites the published protocol, not a checklist of the current audits, and no newer protocol was found as of 2026-10-20.
- **Rule in force only.** The January 6, 2025 HIPAA Security Rule notice of proposed rulemaking (90 FR 898, RIN 0945-AA22) is a proposed rule, not final as of 2026-10-20; the 2026 Unified Agenda lists final action for July 2027 under Long-Term Actions. Nothing proposed in it appears here, and the protocol predates it.
- **A different question from the crosswalk.** The crosswalk's coverage labels ask whether the design covers a provision. This map asks whether the design would produce the records the protocol requests. The answers differ on many rows: the crosswalk counts 13 rows as designed ([crosswalk.md section 5][cws5]), and this map counts one.

## 2. How to read the map

**The policy question on every row.** Nearly every protocol row first asks whether the entity has written policies and procedures for the requirement, and asks to obtain and review them. This repository provides no policies: its ADRs are design records, not Contoso's policies (crosswalk XW-61). That part of every row is Contoso's work, so the "what the auditor asks" column lists only the implementation documentation the protocol requests beyond it.

**Addressable rows (A).** Each addressable row also asks whether the entity chose an alternative measure and, if so, for documentation of why the specification is not a reasonable and appropriate safeguard and "what equivalent alternative measure has been implemented instead". That is the documentation 45 CFR 164.306(d)(3) requires. It is not repeated row by row.

**How the protocol lays out these rows.**
- 164.308(a)(1)(i) is printed as "§164.308(a)".
- 164.308(a)(7)(ii)(E) is printed as "§164.308(a)(7)(ii)(A)"; its key activity and performance criteria identify it as the applications and data criticality analysis.
- 164.308(b)(2) has no row of its own; its text sits in the 164.308(b)(1) row.
- 164.314(a)(2)(i) is split into three rows, (i)(A) to (i)(C), and 164.314(b)(2) into four, (b)(2)(i) to (iv). Each is one row here, as in the crosswalk.
- The Security section opens with rows for 164.306(a), labeled "General requirements, not a part of an audit inquiry", and 164.306(b), flexibility of approach. The crosswalk covers 164.308 to 164.316, so this map does not include them.

**Status.** Status describes the implementation records the protocol asks for, beyond the policies and procedures above.

| Status | Meaning |
|---|---|
| designed | A component or document in the design set would produce the implementation records the row asks for. |
| partial | The design set would produce some of them. The rest depend on procedures, people, or systems the design does not cover, and the cell says which. |
| procedural | The records are policies, plans, contracts, training or personnel records, or other human-process records that no architecture produces, and this repository provides none. |
| gap | The records would come from a technical or physical mechanism that the design set excludes or lacks. |
| not applicable | The provision does not apply to Contoso as the scenario defines it (crosswalk applicability). The row stays so the two files line up. |

**Shorthand.** "01" to "05" are the architecture documents in `architecture/zero-trust-healthcare/`, and "s" means section. ADR-001 to ADR-009 are the decision records, and A-xx, P-x, CA-xx, F-xx, WP-x.x, and RR-xx are the assumptions, design principles, Conditional Access policies, data flows, roadmap work packages, and residual risks those documents define. DX-xx, SN-xx, and SG-xx are rules in the detection pack, and "identity" and "ransomware" are its two incident response playbooks. Component IDs such as `PIP-SIEM` come from the glossary in [02 s11][a02s11]. Every link is relative to this repository.

What the counts say:
- **One row is designed: transmission security (164.312(e)(1)).** Most of the design's technical work lands as partial, because the protocol's requests reach areas the design set excludes: EHR internals (roles, break-the-glass configuration, audit configuration, integrity mechanisms), legacy applications that keep local accounts, and recovery, which is specified as requirements only.
- **Administrative rows are mostly partial.** The design would produce the technical records (identity lifecycle events, privileged access approvals and reviews, activity logs, incident records). The protocol also asks for HR, training, and management certification records that it would not produce.
- **Procedural rows cluster where no architecture helps:** sanctions, the security official, training and reminders, evaluation, business associate agreements, and documentation retention, availability, and updates.
- **Physical safeguards are mostly procedural or gap,** as section 3.2 explains: 3 gap and 4 procedural of 12. The 5 partial rows get there through technical records, not physical ones.
- **Recovery rows rest on requirements.** The data backup, disaster recovery, and testing rows (164.308(a)(7)(ii)(A), (B), and (D)) are partial on ADR-009's requirements alone. No backup or restore record exists until a recovery design meets ADR-009 and restores are tested (RR-11).
- **Four rows are gaps:** facility access controls, the facility security plan, a backup copy before equipment moves, and the mechanism to authenticate ePHI.
