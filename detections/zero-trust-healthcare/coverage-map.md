# Contoso Regional Health (fictional): detection coverage map

> **Reference work.** Fictional scenario built for a public portfolio. Not deployed in, derived from, or describing any employer environment. Not professional advice.

This map shows which behaviors from the threat model the detection pack can see, with which data source, in which rule file, and which attack path each rule answers. It also lists what the pack cannot see yet, so a reader can judge the gaps as well as the coverage. Inputs are `threat-models/zero-trust-healthcare/detection-priorities.md` (20 items; item 19 is the emergency access monitoring that `architecture/zero-trust-healthcare/03-identity-and-access.md` section 5 requires, and item 20 the admin-group monitoring that 03 sections 3 and 4 require) and `attack-paths.md` (AP-1 to AP-7). Component and zone IDs come from `architecture/zero-trust-healthcare/02-reference-architecture.md` section 11, and risk IDs from `grc/zero-trust-healthcare/risk-register.md`.

Technique references use MITRE ATT&CK Enterprise v19.2, checked against MITRE's STIX data for that release. Where v19 renumbered a technique, the current ID is used (for example T1685 for tool tampering).

## 1. Status definitions

| Status | Meaning |
|---|---|
| untested template | Written and reviewed against Microsoft's published schemas and the Sigma specification, never run against any tenant, workspace, or lab |
| lab-tested | Run in an isolated lab with the result recorded in a findings entry (`purple-team-plan.md` section 7) |
| reference | Logic adapted from a published, maintained source and labeled as such |

All 22 rules in this pack are **untested template**. None has been run against data, so none has a measured false positive rate. Static checks last ran on 2026-10-05: all 16 KQL queries parse and pass semantic analysis with no errors or warnings (Microsoft's Kusto.Language library 12.4.1, against table schemas built from Microsoft Learn's Defender XDR and Azure Monitor table references), and all six Sigma rules pass `sigma check` (sigma-cli 3.1.0, pySigma 1.5.1); section 6 records the conversion results. The purple team plan's exercises (PX-01 to PX-20) are the route to lab-tested status for the rules they cover. PX-16 to PX-18 cover DX-05's certificate stage, SN-02's role, policy, and trust branches, and DX-09 and SG-02; PX-17 also carries SN-07's admin-group run. PX-19 is the emergency access drill that validates SN-06, and PX-20 validates SN-07, sharing its runs with PX-17's exclusion-group step and the PX-19 drill. T1557 has no pack rule and no exercise. Microsoft lists Attacker in the Middle as a user risk detection, calculated offline, and documents no path for it into the sign-in rows DX-03 reads, so section 2 credits T1557 to that native Entra ID Protection detection rather than to DX-03. An exercise would also need adversary-in-the-middle phishing infrastructure, which the plan does not stand up.

**Notes to the section 3 table.**

- **Item 9.** DX-07's logon and process signals read DeviceLogonEvents and DeviceProcessEvents, which need Defender for Endpoint, with server licensing, on the `IDS-SYNC` servers. The design places Defender for Identity sensors there (03 section 4) but does not yet state Defender for Endpoint (`threat-model.md` TM-A4 and section 9 item 8). Until the architecture decides, that half has no data, and the item rests on DX-07's Defender for Identity alert signal and SN-02's domain authentication and sync branch.
- **Item 10.** Role assignments and activations are matched against the Tier 0 Entra roles in `03-identity-and-access.md` section 4, Privileged Authentication Administrator, Security Administrator, and Domain Name Administrator included. Application Administrator and Cloud Application Administrator alert at any scope, scoped assignments included: 03 places only tenant scope in Tier 0, so an assignment scoped to one application that is not Tier 0 is closed against its record, and PX-17 records what an app-scoped assignment logs. Any assignment of a role that 03 section 4 says is never assigned (Partner Tier1 Support, Partner Tier2 Support, Windows 365 Administrator, and External Identity Provider Administrator) alerts at High. Outside SN-02: a privileged Entra role outside those lists (PX-17 records it as a coverage gap), and the entries in 03's Tier 0 row that are not Entra directory roles, namely Defender roles that can run live response on all devices, Azure roles that can write to the resources hosting Tier 0 managed identities, and Active Directory Domain Admins and Enterprise Admins. No rule in this pack watches assignments of those roles or membership changes to those groups. Changes to `grp-admins-t0` and `grp-admins-t1` are item 20.
- **Item 11.** Grants of any permission in the table in `03-identity-and-access.md` section 6 score High, delegated grants of the same names included; an application permission grant makes the application a Tier 0 workload identity (03 section 4). The table is not exhaustive, so SN-03's pattern follows it as it grows. Any credential added to a Tier 0 workload identity also scores High, approved automation included. Gap: managed identity sign-in monitoring is not built. CA-22 does not cover managed identities (03 section 6), and SN-03 watches consents and credentials, not sign-ins.
- **Item 19.** SN-07 matches the group and the accounts by object ID, not by activity name, and leaves Conditional Access policy changes that name the group to SN-02 (item 10). Removing an account from the group, or deleting the group, carries no ATT&CK technique (`threat-model.md` TB-7, denial of service). SN-06 alerts on every sign-in by the two tenant emergency access accounts, and SN-07 on every change to `grp-ca-emergency-access` and all audit activity by or on the accounts. Together they are the emergency-account alerting that `attack-paths.md` AP-5 steps 8, 8a, and 8b and `threat-model.md` TB-7 name.
- **Item 20.** Administrator joiners and leavers are closed against their change records. Conditional Access policy changes that name the groups are left to SN-02 (item 10). Item 20 extends SN-07's group watch to `grp-admins-t0` and `grp-admins-t1`, where removing an admin account is step 8a's move in the other direction: the account leaves the phishing-resistant and PAW-only policies (CA-03, CA-04, CA-05) with no policy edited. As item 20 maps them, an admin account's removal or a group's deletion carries T1556.006 (Modify Authentication Process: Multi-Factor Authentication), and an owner added or a role assigned carries T1098.003 (Account Manipulation: Additional Cloud Roles); an added member, a removed owner, a rename, or a restoration carries none.

## 6. Conversion notes for the Sigma rules

| Rule | Log source | Defender XDR backend (pySigma Kusto, microsoft_xdr pipeline) |
|---|---|---|
| SG-01, SG-02, SG-03, SG-04 | Windows process creation | The pipeline targets this log source. On 2026-10-04, `sigma convert -t kusto -p microsoft_xdr` (pySigma-backend-kusto 1.0.1) converted all four to DeviceProcessEvents queries, which have not been run against data |
| SG-05, SG-06 | Windows Security log (4769, 4662) | Not expected to convert cleanly: Defender XDR's native advanced hunting schema has no raw Windows Security event table, and the microsoft_xdr pipeline maps only to native Defender XDR device tables. The 2026-10-04 conversion run stopped with an error on both and produced no query, as predicted. The Defender XDR equivalents are DX-05 and DX-06. A Sentinel version queries SecurityEvent, which can also be queried from advanced hunting once the Sentinel workspace is onboarded to the Defender portal. SecurityEvent has columns for the 4662 fields SG-06 uses, but none for the 4769 ticket encryption type, which SG-05 reads from EventData |

No Sigma correlation rule is included. The AP-2 chain is written directly in KQL as SN-01, because the Kusto backend has no correlation support.

## 7. Open items outside the rules

The identity compromise playbook (`playbooks/ir-identity-compromise.md` section 1) leaves three response areas out of scope and points here.

- **Ransomware response beyond identity.** The pack ships one playbook, for identity compromise. Ransomware encryption, containment, and restoration steps depend on recovery. ADR-009 sets the recovery requirements a later ransomware playbook builds on: immutable and offline copies, isolation from Tier 0 administrative reach, tested restores with evidence, and Tier 0 monitoring. The implementation is not designed, so recovery capability is unverified (RR-11). DX-01, DX-02, and DX-09 route to Branch D of the identity playbook for the identity side.
- **Medical device containment beyond the clinical safety gate (AP-7).** The pack has no rule for medical device segments (section 4), and any device containment follows the clinical safety gate (`04-segmentation.md` section 3, ADR-008).
- **Misuse of legitimate EHR access (RR-01).** Authorized users browsing or bulk-pulling records within their role belong to EHR privacy monitoring, which is outside this design (risk register R-09).
