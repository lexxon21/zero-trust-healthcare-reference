# Contoso Regional Health (fictional): identity and access design

> **Reference work.** Fictional scenario built for a public portfolio. Not deployed in, derived from, or describing any employer environment. Not professional advice.

This document covers the cloud identity plane for Contoso Regional Health (fictional): identity populations, authentication strategy, the reference Conditional Access policy set, privileged and emergency access, workload identities, vendor and B2B access, and patient identity separation. Component IDs refer to the glossary in `02-reference-architecture.md` section 11. Assumptions A-01 to A-19 are in `01-scenario-and-assumptions.md`.

## 1. Identity populations and lifecycle

|---|---|---|---|---|

## 2. Phishing-resistant MFA strategy

Decision record: ADR-003. Microsoft's built-in "Phishing-resistant MFA" authentication strength accepts three method types:
- Windows Hello for Business or platform credential.
- FIDO2 security key, which the authentication methods policy now calls Passkey (FIDO2).
- Certificate-based authentication (multifactor).

Authentication strengths require Microsoft Entra ID P1, which Microsoft 365 E5 includes.

| Persona | Primary method | Why | Rollout phase (05) |
|---|---|---|---|
| Tier 0 and Tier 1 administrators | Device-bound FIDO2 security keys, used on PAWs | Highest impact accounts; keys are portable across PAWs | Phase 1 |
| Remote workforce and ZTNA users | Windows Hello for Business on assigned laptops (cloud Kerberos trust for on-premises SSO) | Bound to the device that is also checked for compliance | Phase 1 |
| Vendors and the outsourcer | Home-tenant phishing-resistant methods under inbound MFA trust, or Contoso-issued security keys (section 7) | External accounts with privileged or high-volume ePHI access | Phase 1 |
| Corporate staff on assigned devices | Windows Hello for Business | No extra hardware | Phase 2 |
| Clinicians at shared clinical workstations | Smart card badge carrying a PIN-protected certificate. It signs in to Windows against the local domain and to Entra ID through certificate-based authentication (multifactor). | Phishing-resistant and works when the hospital loses internet (ADR-003, ADR-008) | Phase 2 to 3 |
| Clinicians and affiliated physicians on phones | Passkey in Microsoft Authenticator | No extra hardware for non-employees | Phase 2 |

Supporting rules:

- **Device-bound passkeys.** A passkey profile allow-lists approved authenticator models by AAGUID and enforces attestation where the authenticator supports it. Microsoft warns that without attestation it cannot guarantee whether a passkey is synced or device-bound. Synced passkeys are not accepted for workforce accounts in phases 1 and 2. Microsoft's persona guidance describes synced passkeys as a good option for frontline workers, so this is a deliberate choice of control over convenience, revisited in phase 3.
- **Onboarding and recovery.** New users and users who have lost their method receive a Temporary Access Pass after identity proofing: in person at a badge office, or through a named sponsor for vendors and for staff who cannot reach a badge office. There is no phone-only path: a call to the service desk never, on its own, issues a Temporary Access Pass or changes a user's registered methods. A Temporary Access Pass satisfies the MFA strength but is not phishing-resistant. Its only use is registering a phishing-resistant method (CA-19). A Temporary Access Pass cannot be added to an external guest account, and every guest in this design is external (section 7).
- **Registration protection.** Microsoft announced that from July 6, 2026, Conditional Access policies that target "Register security information" also apply to Windows Hello for Business and macOS Platform SSO credential registration. On 2026-10-04 its page still described the change as upcoming, so whether it has taken effect is not confirmed. CA-19 therefore has to be validated in report-only mode against those registration flows before enforcement.
- **Methods retired.** SMS and voice are disabled for workforce accounts. The one exception is a migration exception group with an owner and an expiry date. Number-matching push is accepted as an interim method for non-privileged users until their persona's rollout phase completes.

## 3. Reference Conditional Access policy set

This is the reference set for the cloud identity plane. Values marked "example" show the shape of a decision, not a recommendation to copy. On-site clinical access from `Z-CLIN-USER` to the EHR full client, and to the other applications in ADR-008's local-first set, does not pass through these policies; it runs on the local clinical plane (ADR-001, ADR-008). On-site `Z-CORP` laptops do pass through them (CA-11).

Conventions:

- **Groups.** Policies target groups that identity governance maintains:
  - `grp-workforce` (employees and contractors)
  - `grp-affiliated-physicians`
  - `grp-admins-t0` and `grp-admins-t1` (dedicated admin accounts)
  - `grp-pr-enforced` (users whose persona has completed phishing-resistant rollout)
  - `grp-ext-ehr-vendor`, `grp-ext-biomed`, `grp-ext-rcm` (external identities)
  - `grp-vendor-members` (Contoso-managed vendor accounts)
  - `grp-ca-emergency-access`
- **Emergency access.** Following Microsoft's guidance, emergency access accounts are excluded from every enforced policy that blocks or restricts sign-in, through `grp-ca-emergency-access`. Report-only policies need no exclusion.
- **Three groups are Tier 0 objects.** `grp-ca-emergency-access` decides who escapes the blocking policies, and `grp-admins-t0` and `grp-admins-t1` decide who the admin policies cover (CA-03, CA-04, CA-05). All three are role-assignable groups with no owners and no role assigned, so only Tier 0 can change their membership, and every change to them alerts at Tier 0 priority (note 9).
- **Other policy groups are ordinary groups.** Identity governance maintains them from the systems of record, and exception groups, such as CA-20's, carry an owner and an expiry (P-5). A change to one can alter which controls apply to its members, but it needs no Tier 0 activation.
- **Authentication strengths over the MFA control.** Policies use "Require authentication strength", never "Require multifactor authentication". The two cannot be combined in one policy, and strengths make the accepted methods explicit.
- **Rollout.** Every policy starts in report-only mode and is reviewed against sign-in logs before enforcement (P-6).
- **Device tags.** Device roles live in `extensionAttribute1` (`PAW-T0`, `PAW-T1`, `SHARED-CLIN`). CA-04 and CA-05 accept a device as a PAW by this tag, so writing it is Tier 0 work (ADR-004 decision 6):
  - Writers. The applications and roles that can write the tag are Tier 0, except Windows 365 Administrator, which is never assigned; a planned lab test settles whether that role, and a device's registered owner, can write it (note 10).
  - Evaluation. Filter for devices can read extension attributes only for devices that are Intune managed, compliant, or Microsoft Entra hybrid joined. Unregistered devices evaluate as null, so negative and exclude logic is used where unregistered devices must be caught.

**Notes to the policy table.**

1. **CA-06.** Microsoft's PIM guidance says this policy should include all users or the role's eligible users. Targeting all users keeps these requirements independent of membership in the admin groups. CA-06 does not read the PAW tag: for admin accounts, the PAW requirement comes from CA-04 and CA-05, which target `grp-admins-t0` and `grp-admins-t1`. Microsoft documents this pattern to enforce reauthentication on every role activation (generally available April 2026), with a 10-minute window: after a user reauthenticates for one activation, activating another eligible role within that window does not prompt again, across Microsoft Entra roles, Azure resource roles, and PIM for Groups. Microsoft's PIM guidance also names Conditional Access Administrators and Security Administrators as able to change or remove activation requirements, and says anyone who can manage Conditional Access should be treated as highly privileged, so both roles are Tier 0 (section 4).
2. **CA-10.** Session controls work in browsers only; desktop clients on unmanaged devices are blocked by CA-08. Sign-in frequency limits session length but is not an inactivity timeout; how idle sessions end on this path is in `02-reference-architecture.md` section 9.
3. **CA-11.** The compliant network check is not supported for Private Access apps. Private Access is a licensed add-on (ADR-002). Applies on site as well: Intelligent Local Access is not used, so on-site `Z-CORP` laptops reach these apps only through the tunnel and lose them when the hospital loses internet (ADR-008).
4. **CA-13.** CA-13b covers Contoso-managed vendor accounts, which are members, not guests, so CA-13a does not reach them (section 7). Vendors request activation of their session group in the Microsoft Entra admin center, where Microsoft documents PIM for Groups activation. Windows Azure Service Management API is the target Microsoft points to for controlling access to the admin center: it covers the Azure portal, and with it the admin center, plus Azure Resource Manager, Azure Data Lake, Application Insights API, and Log Analytics API. The Microsoft Admin Portals grouping also contains the Azure portal, but it adds three other admin portals, and Microsoft describes it as intended mainly for include scenarios. The tradeoff: vendor accounts hold no Azure role or directory role, so the exclusion gives them only default user permissions there, which Microsoft restricts for guests but which let Contoso-managed member accounts read most directory information. Before enforcement, both parts run in report-only mode, and the run must show a vendor's activation request completing; for CA-13b it must also show the Temporary Access Pass registration flow completing, which these accounts use to register their security key (section 2, CA-19a). Any further resource either flow needs, as the audience reporting in the sign-in logs shows, is excluded by name and listed in CA-13's row. The run also checks the enforcement described on Microsoft's baseline scopes page, which Microsoft is rolling out for policies that target all resources with resource exclusions: a sign-in that requests only baseline scopes is evaluated as directory access, and Microsoft names block policies among the cases affected, so it can block a sign-in to an excluded app.
5. **CA-14.** CAE does not support guest accounts, so a short sign-in frequency compensates. Vendor session length is bounded separately by the PIM for Groups activation window.
6. **CA-17.** For guests, sign-in risk policies work only if the guest registered MFA in Contoso's tenant, which this design never does.
7. **CA-18.** Guest user risk is evaluated and remediated only in the home tenant, and risk remediation is not supported for guests. Microsoft gave October 1, 2026 as the retirement date for the legacy ID Protection risk policies; on 2026-10-04 its pages still worded the retirement as upcoming. Either way, risk policy lives here. On 2026-10-03, Microsoft's documentation showed the risk remediation control without a preview label but with no dated general availability entry. Confirm its status before enforcement.
8. **CA-21.** Generally available for native apps on Windows; browser support is in preview. Recheck Apple platform status before extending, because the documentation is inconsistent. Starts in report-only mode.
9. **Three groups are Tier 0 objects.** Microsoft documents that a tenant-level Groups Administrator, or an application holding Group.ReadWrite.All, can change an ordinary group's membership (ADR-004 alternative F). Removing an admin account from an ordinary admin group would take it out of the PAW-only rule with no Tier 0 step, so all three are created as role-assignable groups, with no owners and no role assigned:
   - Changing their membership needs an active Privileged Role Administrator or Global Administrator assignment, or an application holding RoleManagement.ReadWrite.Directory, which is Tier 0 (section 6). Section 5 lists Microsoft's documented restrictions for these groups.
   - Microsoft documents that changing the credentials, resetting MFA, or modifying sensitive attributes of a role-assignable group's members needs at least Privileged Authentication Administrator. Microsoft also warns that assignments activated without approval are exposed to less-privileged administrators who might reset a user's credentials and activate on their behalf. Membership closes that path for every admin account. It matters most in Tier 1, where most activations need no approval (section 4).
   - Membership is changed by a Tier 0 administrator against a change record, not by lifecycle automation. Every change to the members, owners, or properties of any of the three raises an alert at Tier 0 priority (sections 4 and 5).
10. **Device tags: Writers.** Microsoft documents that device extension attributes are mastered in the cloud, so directory synchronization does not set them. Its reference for updating a device lists Device.ReadWrite.All and Directory.ReadWrite.All as the application permissions, and an application holding either is a Tier 0 workload identity (section 6). A role can write the tag if its definition includes `microsoft.directory/devices/extensionAttributeSet1/update`. Of the built-in role definitions checked on 2026-10-04, Intune Administrator's and Windows 365 Administrator's include it, and Global Administrator's includes `microsoft.directory/devices/allProperties/allTasks`. Microsoft's list of device permissions for custom roles includes no extension attribute permission. Global Administrator and Intune Administrator are Tier 0, Windows 365 Administrator is never assigned, and every other role is checked for the permission before its first assignment (section 4). Microsoft's pages disagree on whether Windows 365 Administrator, and a device's registered owner, can write the tag, and the lab test settles it (appendix: Entra role edge cases checked). If the owner's call is accepted, the tag alone cannot mark a PAW, and CA-04 and CA-05 need a second device signal (ADR-004 Revisit when).

Controls deliberately not used:

| Not used | Reason |
|---|---|
| Country blocking for the workforce | Clinicians travel and on-call staff work remotely. Country locations are coarse, and they are not CAE-aware: country-based locations fall back to one-hour tokens. Risk-based policies (CA-17, CA-18) do more. |
| "Require Microsoft Entra hybrid joined device" as a grant | Proves domain membership, not device health. CA-08 requires compliance instead. |
| Compliant network check for private apps | Not supported for Private Access apps. CA-11 relies on device compliance and authentication strength instead. |
| Trusted-location exclusions for MFA or registration | Hospitals have public spaces and guest networks next to clinical ones, so being on-site is not a trust signal. |
| CAE strict location enforcement | Public preview at the time of writing |

## 4. Privileged access model

Decision record: ADR-004.

| Tier 2, user and workstation support | Endpoints and user support | Service desk, desktop support | Dedicated support accounts on managed support workstations | Scoped roles. Windows LAPS for local administrator passwords. No server access. |

Rules:

- **No standing privilege.** Every privileged assignment is eligible-only through PIM. The two emergency access accounts are the only permanent active Global Administrators. PIM, PIM for Groups, and PIM Conditional Access controls are included in Entra ID P2. Microsoft Graph application permissions sit outside the roles and groups PIM manages, so a Tier 0 workload identity's permissions are standing grants (RR-16).
- **Cloud admin accounts are cloud-only.** Privileged users are not synchronized from on-premises Active Directory, so an on-premises compromise does not hand over cloud administration. This follows Microsoft's guidance.
- **Activation requires authentication context `c1` (CA-06).** CA-06 requires a phishing-resistant method and a compliant device, with sign-in frequency set to every time, for any account: it targets all users, so these requirements hold whichever groups an account is in. The PAW requirement comes from CA-04 and CA-05, which apply through `grp-admins-t0` and `grp-admins-t1`, so it holds for the accounts in those groups, whose membership changes only through Tier 0 (section 3). Microsoft documents a 10-minute window: after a user reauthenticates for one activation, activating another eligible role within 10 minutes does not prompt again, across Microsoft Entra roles, Azure resource roles, and PIM for Groups. Each Tier 0 activation still needs its own approval (below).
- **Resetting an administrator's credentials is Tier 0 work.** Microsoft documents that Privileged Authentication Administrator can manage the authentication methods of all users and can reset a Global Administrator's password, which Helpdesk, Password, Authentication, and User Administrators cannot do. A holder of that role could take over any Tier 0 account, including the emergency access accounts, which no enforced Conditional Access policy restricts (section 5). It is therefore a Tier 0 role with Tier 0 PIM settings. Microsoft documents that the deprecated Partner Tier2 Support role can also reset Global Administrator passwords; it is never assigned (below).
- **Changing Conditional Access is Tier 0 work.** Microsoft's PIM documentation says that principals who can manage Conditional Access policies, such as Conditional Access Administrators or Security Administrators, can change or remove activation requirements or block eligible users from activating, and should be considered highly privileged. Microsoft lists Security Administrator alongside Conditional Access Administrator for creating policies and managing named locations. Both roles are therefore Tier 0, with Tier 0 PIM settings.
- **Security Administrator also reaches every device.** Microsoft's Defender for Endpoint documentation grants full access to users with the Security Administrator role, through the Defender for Endpoint Global Administrator role, which has unrestricted access to all devices. That page describes Defender for Endpoint's own role model, and notes that customers new to Defender for Endpoint from February 16, 2025 have only unified role-based access control. The Tier 0 placement does not rest on this reason alone: the Conditional Access reason above applies either way. Where the Defender for Endpoint model applies, it meets this tier's test of control over every device, the same test that makes Defender live response roles Tier 0. Security operations work that needs neither Conditional Access changes nor fleet-wide device control uses narrower roles that stay below Tier 0.
- **Changing how a domain authenticates is Tier 0 work.** Contoso uses managed authentication with no federation service (A-01), so a change to a domain's federation settings would let another identity provider authenticate that domain's users. Microsoft documents that Domain Name Administrator can configure domain names for federation and manage Microsoft Entra Connect, and its definition includes `microsoft.directory/domains/allProperties/allTasks`. Microsoft names it the least privileged role for managing domains, which Contoso still does, so it is a Tier 0 role with Tier 0 PIM settings rather than a role that is never assigned. Hybrid Identity Administrator, already Tier 0, holds `microsoft.directory/domains/federation/update`, and so does External Identity Provider Administrator, which is never assigned (below).
- **Tier 0 applications are administered only from Tier 0.** Microsoft documents that:
  - Application Administrators can add credentials to an application and use them to impersonate it, doing whatever the application's identity is allowed to do. Cloud Application Administrator has the same permissions except managing application proxy.
  - An application's owners have the same permissions as an Application Administrator, scoped to that application.
  - Custom roles, and some built-in roles (Microsoft's example is Application Administrator), can be assigned at the scope of a single application.
  - Applications that hold highly privileged roles are control plane (Tier 0) intermediaries, to be administered only from equally trusted systems.

  The design applies those statements as follows:
  - Application Administrator and Cloud Application Administrator are Tier 0 when assigned at tenant scope. Routine application work uses app-scoped assignments, which are Tier 1 when the application is not Tier 0.
  - Tier 0 applications have no owners in the directory. Their accountable owner is recorded in the application owner registry and in the application's service management reference, which Microsoft recommends for team contact information.
  - A credential added to a Tier 0 application outlives the activation or automation run that added it. Only a Tier 0 administrator, or approved automation that is itself Tier 0, adds one, against a change record. SN-03 alerts at High on every credential added to a Tier 0 workload identity, whoever adds it, approved automation included (`coverage-map.md` section 3, item 11). On that path the alert is the control (RR-16).
- **Tier 0 managed identities are administered as Tier 0.** Microsoft documents that a managed identity's security boundary is the resource it is attached to, that any code running there can request its tokens, and that using a system-assigned identity needs write access to that resource. A managed identity that holds a Tier 0 permission, such as a Sentinel automation identity with directory write permissions, is therefore system-assigned, which Microsoft documents cannot be shared with another resource. Its resource sits in an Azure scope reserved for Tier 0 automation. Azure role assignments are inherited from higher scopes, so every role assignment that can write to that scope, at it or above it, is Tier 0 and eligible through PIM with Tier 0 settings.
- **Applications that can issue a Temporary Access Pass are Tier 0.**
  - Why: Microsoft's reference for creating a Temporary Access Pass lists UserAuthMethod-TAP.ReadWrite.All and UserAuthenticationMethod.ReadWrite.All as application permissions, and states a role requirement only for delegated calls. That role requirement is what protects administrators: Microsoft's Temporary Access Pass guidance lets an Authentication Administrator issue a pass only to non-administrators. Microsoft's permissions overview says an application permission gives access to any data it is associated with. So an application granted either permission can issue a pass to any user, Global Administrators and the emergency access accounts included, with no role, activation, or approval.
  - Read permissions: an application holding either read permission Microsoft's reference also lists for the call (UserAuthMethod-TAP.Read.All, UserAuthenticationMethod.Read.All) is Tier 0 until the lab test shows it cannot create a pass (appendix: Entra role edge cases checked).
  - Default: administrators issue passes through delegated access, after identity proofing (section 2). No application holds any of the four permissions.
  - Exception: an application that must hold one is a Tier 0 workload identity, like one granted RoleManagement.ReadWrite.Directory (section 5). Microsoft documents that only Privileged Role Administrators and Global Administrators can consent to application permissions. The other route to a grant, an application that can assign app roles, is itself Tier 0 (section 6). A grant therefore needs a Tier 0 administrator or a Tier 0 workload identity, and is made against a change record. Like every application permission grant, it raises an alert (SN-03; `coverage-map.md` section 3, item 11).
  - Residual: nothing gates the application's use of the permission, so on that path the alert on the change it makes is the control (RR-16). For the emergency access accounts, that alert comes from SN-07 (section 5). On any other Tier 0 account a pass yields less, because the account still needs a phishing-resistant sign-in from a Tier 0 PAW and an approved activation before it can use a role (CA-03, CA-04, CA-06).
- **Roles that are never assigned.** The design never assigns the roles below. Each has a definition that reaches Tier 0, and each is deprecated or exists for a function Contoso does not use. Any assignment of one raises an alert (Monitoring, below).
  - Partner Tier1 Support and Partner Tier2 Support. Microsoft says both are deprecated and should not be used. Both role definitions include updating any application's credentials and owners (`microsoft.directory/applications/credentials/update` and `microsoft.directory/applications/owners/update`), which reaches Tier 0 applications. Partner Tier2 Support can also reset Global Administrator passwords.
  - Windows 365 Administrator. Its definition includes `microsoft.directory/devices/extensionAttributeSet1/update`, which covers the device tag that CA-04 and CA-05 read, although Microsoft's reference for updating a device says the role can update only basic device properties (section 3). Windows 365 is not part of the scenario stack in `01-scenario-and-assumptions.md`. If Contoso adopts it, the role is Tier 0, with Tier 0 PIM settings, unless the lab test in section 3 shows it cannot write the tag.
  - External Identity Provider Administrator. Its definition includes `microsoft.directory/domains/federation/update` and `microsoft.directory/identityProviders/allProperties/allTasks`, and Microsoft labels it privileged. Contoso accepts external identities only from partners that authenticate with Entra ID (section 7), so it configures no external identity provider.
- **Every role is checked before its first assignment.** The Tier 0 row and the list above name the roles this design checked against Microsoft's documentation on 2026-10-04. They are not a review of every role Microsoft offers. Before any role, built-in or custom, is first assigned, its definition is checked against the Tier 0 scope in the table above: control of identity, or the ability to run code on every device. The scope includes, for example, changing role assignments or role-assignable group membership, administrators' credentials or authentication methods, Conditional Access, domain federation and authentication settings, an application's credentials or owners, or the device tags that CA-04 and CA-05 read; running code on every device; and running code on a PAW or a Tier 0 server, or reading a secret that unlocks one, such as a BitLocker recovery key or a local administrator password, unless the assignment is kept from those devices (`02-reference-architecture.md` section 7). A role that reaches the scope is Tier 0 or never assigned. The check covers role assignments in Microsoft Entra ID, Intune, Defender, and Azure, and administrative group membership and delegated rights in Active Directory. Microsoft's privileged label does not decide the question: the label is in preview, and Windows 365 Administrator's definition carries no privileged label. Application permissions get the same check before they are granted (section 6).
- **Approvals.** Microsoft requires at least one approver and recommends two. If every Privileged Role Administrator and Global Administrator assignment is eligible, approval is required, and no approver is set, Microsoft warns the tenant can be locked out. The design names two approvers per Tier 0 role, and the emergency accounts cover the remaining lockout risk.
- **Safety-critical consoles.** Changes to medical device management consoles need two-person control: a PIM approval by clinical engineering plus the clinical change process.
- **Privileged access workstations (`PEP-PAW`).**
  - Configuration: Entra joined, managed under a dedicated Tier 0 Intune scope, with application allow-listing. No email or general web browsing.
  - Network: only the PAW subnet in `Z-MGMT` can reach management interfaces.
- **On-premises Active Directory.**
  - Separate administrator accounts per tier, with Group Policy denying logon across tiers.
  - The Protected Users group, and authentication policies and silos, for Tier 0 accounts.
  - Windows LAPS for local administrator passwords.
  - No Tier 0 logon on Tier 1 or Tier 2 hosts.
  - Defender for Identity sensors on every domain controller, on AD CS servers that hold the Certification Authority role, and on the active and staging Entra Connect servers. The two qualifiers come from Microsoft's sensor v2.x prerequisites page, which lists AD CS and Entra Connect servers that are not domain controllers among the servers the v2.x sensor supports.
- **Monitoring.** Sentinel alerts on PIM activations, role assignment changes, Conditional Access policy changes, domain authentication and federation changes, emergency account sign-ins and audit activity, changes to `grp-ca-emergency-access`, `grp-admins-t0`, and `grp-admins-t1`, grants of the permissions in section 6, credentials added to Tier 0 applications, and changes to directory synchronization. Changes to `grp-admins-t0` and `grp-admins-t1` alert like changes to the exclusion group (section 5): matched by object ID, at Tier 0 priority, with no exclusion for planned work. SN-02, SN-03, SN-06, and SN-07 implement these alerts; `coverage-map.md` section 3 (items 9 to 11, 19, and 20) records what each covers, and the gap for other privileged roles (item 10). Every detection rule named in this document is an untested template as of 2026-10-04 (`coverage-map.md` section 1).

## 5. Emergency access: three different kinds of "break glass"

Healthcare uses "break glass" for three unrelated things, and a design that blurs them fails audits and incidents alike.

| Concept | Purpose | Design |
|---|---|---|
| Tenant emergency access accounts | Recover administration of Entra ID when normal admin access fails, for example after a Conditional Access mistake or an MFA outage | Follows Microsoft's emergency access guidance (details below) |
| On-premises AD recovery credentials | Recover Active Directory when domain administration is lost | Sealed, offline credentials for a Tier 0 recovery account and Directory Services Restore Mode. Split custody. Used only under incident command and rotated after use. |
| Clinical break-the-glass in the EHR | Let a clinician open a patient record outside their normal assignment in an emergency | An EHR feature: justification captured, access audited, privacy review afterward. Part of the HIPAA emergency access procedure, 45 CFR 164.312(a)(2)(ii) (required). Configuration is out of scope. |

Tenant emergency access account design:
- **Accounts.** Two cloud-only accounts on the `onmicrosoft.com` domain, each a permanent active Global Administrator.
- **Authentication.** Passkey (FIDO2) security keys, different from the methods normal admin accounts use. Mandatory MFA applies to these accounts and passkeys satisfy it.
- **Storage.** Fireproof safes at two different hospitals, with split custody: one custodian holds the key, another holds the PIN.
- **Conditional Access.** Excluded only from policies that block or restrict sign-in, through `grp-ca-emergency-access`. The exclusion has no expiry date, so it is the deliberate exception to P-5 (`01-scenario-and-assumptions.md`). In place of an expiry it has an owner (security governance), the change controls below, and a membership check at every validation.
- **The exclusion group is a Tier 0 object.** An account added to `grp-ca-emergency-access` escapes every enforced policy that blocks or restricts sign-in, including baseline MFA (CA-02), legacy authentication blocking (CA-01), the risk policies (CA-17, CA-18), and the PAW-only rules (CA-04, CA-05). Removing an emergency account, or deleting the group, takes away the lockout backstop. Changes to the group are therefore approval-gated and monitored at Tier 0 priority (ADR-004 decision 9).
  - **Approval-gated.** The group is created as a role-assignable group, with no owners and no role assigned to it. Microsoft documents that for such a group:
    - The role-assignable setting can be chosen only when the group is created, and never changed afterward.
    - Membership must be assigned, never dynamic.
    - Privileged Role Administrators manage membership by default. Owners can manage it only if they are added.
    - Microsoft Graph requires RoleManagement.ReadWrite.Directory to change membership; Group.ReadWrite.All does not work.
    - No group can be nested inside it.

    A membership change therefore needs an active Privileged Role Administrator or Global Administrator assignment. For an administrator, that is a Tier 0 activation approved by one of two named approvers, on a Tier 0 PAW (section 4), made against a change record. Two kinds of identity can change the group with no approval: the emergency accounts themselves, which are permanent Global Administrators, and an application granted RoleManagement.ReadWrite.Directory, which is a Tier 0 workload identity (section 4). On those paths the alert on every change is the only control (RR-16).
  - **Monitored at Tier 0 priority.** A change to the group's members, owners, or properties, and the group's deletion or restoration, each raise a Sentinel alert at the same priority as an emergency account sign-in. No time-of-day filter or planned-work exclusion applies: a planned change is closed against its change record. Changing which group a policy excludes is a Conditional Access policy change, which already raises an alert (section 4).
- **Monitoring and testing.**
  - Every sign-in raises a Sentinel alert.
  - So does audit activity by either account, and every change made to either account: authentication methods registered, changed, or deleted; a password reset; the account disabled or deleted; or its Global Administrator assignment removed. Microsoft's guidance is to alert on all sign-in and audit log activity for these accounts. A change made to an account comes before any sign-in it enables, so it is the earlier signal of the takeovers described in section 4: by a holder of Privileged Authentication Administrator, or by an application that can issue a Temporary Access Pass.
  - The accounts are validated at least every 90 days. Each validation also confirms that `grp-ca-emergency-access` holds exactly the two accounts and has no owners.
  - Sign-in is tested against the current Conditional Access set every quarter.
  - Detection: the companion detection pack alerts on every sign-in (SN-06), and on every change to the group and all audit activity by or on the accounts (SN-07), as `coverage-map.md` section 3, item 19 records (status: section 4, Monitoring).
- **Use.** Only from a designated PAW.

## 6. Workload identities

| Workload type | Identity | Credential | Policy |
|---|---|---|---|
| Azure-hosted services: portal back end, integration services, analytics | Managed identities | None stored; the platform manages them | Least-privilege role assignments. Conditional Access for workload identities does not cover managed identities, so their sign-ins need monitoring instead; the companion detection pack records this as an open gap (`coverage-map.md` section 3, item 11). A managed identity that holds a permission in the table below is system-assigned and administered as Tier 0 (section 4). |
| On-premises integration services and automation that call Microsoft APIs | Single-tenant service principals | Certificates held in a key vault. No client secrets for new registrations, except a documented exception with an expiry. | CA-22 where licensed. A named accountable owner in the application owner registry, and a quarterly (example) permission review. A Tier 0 application has no owners in the directory (section 4). |
| Third-party multitenant SaaS apps | Enterprise applications | Vendor-managed | Admin consent workflow; user consent restricted; permission reviews |
| On-premises services | Group managed service accounts where supported, otherwise legacy service accounts | Long random passwords, AES-only Kerberos encryption, no interactive logon, owner on record | Defender for Identity monitoring; migration to group managed service accounts |
| Clinical integration engine interfaces | One identity per interface | Certificates, with mutual TLS where both endpoints support it | Every interface is a documented flow in the access matrix |

Mandatory MFA enforcement does not affect workload identities. User-scoped Conditional Access policies do not apply to calls made by service principals, which is why CA-22 exists.

An application, or a managed identity, is a Tier 0 workload identity (section 4) if it holds an application permission that can change a Tier 0 object or a control that Tier 0 depends on. The table names the permissions this design checks for, each from Microsoft's Graph reference for the operation. The list is not exhaustive, so every application permission is checked against the rule before it is granted.

| Reach | Application permissions | Microsoft reference |
|---|---|---|
| Role assignments, and the membership of role-assignable groups | RoleManagement.ReadWrite.Directory | Create unifiedRoleAssignment; Use Microsoft Entra groups to manage role assignments |
| Granting application permissions, including the others in this table. The reference states its role requirement (Privileged Role Administrator for Microsoft Graph app roles) only for delegated calls. | AppRoleAssignment.ReadWrite.All; Application.ReadWrite.All | Grant an appRoleAssignment for a service principal |
| Adding a credential to any application, Tier 0 applications included | Application.ReadWrite.All; Directory.ReadWrite.All | application: addPassword |
| Issuing a Temporary Access Pass to any user, or changing any user's authentication methods | UserAuthMethod-TAP.ReadWrite.All; UserAuthenticationMethod.ReadWrite.All; and, until the lab test in section 4, UserAuthMethod-TAP.Read.All and UserAuthenticationMethod.Read.All | Create temporaryAccessPassMethod |
| Changing Conditional Access policies | Policy.ReadWrite.ConditionalAccess | Update conditionalAccessPolicy |
| Changing the device tags that CA-04 and CA-05 read | Device.ReadWrite.All; Directory.ReadWrite.All | Update device |

The same addPassword reference lists Application.ReadWrite.OwnedBy, which reaches only the applications its holder owns. That is one more reason Tier 0 applications have no owners in the directory.

## 7. Vendor and B2B access

Decision records: ADR-002 (vendor broker instead of ZTNA) and ADR-004 (just-in-time elevation).

| Partner | Identity model | MFA source | Device trust | Access path | Lifecycle | Monitoring |
|---|---|---|---|---|---|---|
| EHR vendor (`EXT-VENDOR-EHR`) | B2B guests from the vendor tenant | Home-tenant phishing-resistant methods under inbound MFA trust (CA-14) | Not trusted; the broker isolates sessions | `PEP-VENDOR-BROKER` only. Just-in-time through PIM for Groups eligible membership in `grp-vendor-ehr-session`, approved by the Contoso system owner. | Access package approved by a named Contoso sponsor set as a specific approver, 90-day expiry (example); quarterly review (example cadence) | Session recording, broker logs, and PIM activations in `PIP-SIEM` |
| Biomedical vendors with an Entra tenant | B2B guests | Home-tenant phishing-resistant methods under inbound MFA trust | Not trusted | `PEP-VENDOR-BROKER`, limited to that vendor's devices. Just-in-time through PIM for Groups eligible membership in that vendor's own session group, `grp-vendor-biomed-<vendor>-session`, approved by clinical engineering. | As above, with a clinical engineering sponsor | As above |
| Biomedical vendors without an Entra tenant | Contoso-managed, cloud-only member accounts in `grp-vendor-members` | Contoso-issued FIDO2 security key, registered after identity proofing with a Temporary Access Pass, and required at the broker (CA-14) | Not applicable | `PEP-VENDOR-BROKER` only, limited to that vendor's devices. Just-in-time through the same per-vendor session group, approved by clinical engineering. CA-13b blocks every resource except the broker and the PIM for Groups activation surface (section 3). | Access package with expiry; accounts disabled between engagements | As above |
| Revenue-cycle outsourcer (`EXT-RCM-BA`) | B2B guests from the outsourcer tenant | Home-tenant phishing-resistant methods under inbound MFA trust (CA-14) | Outsourcer compliance claims trusted after due diligence (CA-15) | `PEP-APP-PROXY` to the EHR browser interface with billing roles only; managed file transfer for files | Access package; quarterly review (example cadence). When the outsourcer disables a leaver's home account, sign-in fails; package expiry is the backstop. | Sign-in logs, EHR audit logs, data loss prevention on file transfer |

Vendor session groups follow one naming pattern: `grp-vendor-ehr-session` for the EHR vendor, and one `grp-vendor-biomed-<vendor>-session` group per biomedical vendor. A group per biomedical vendor lets the broker map each group to that vendor's devices only, and the shared pattern (`grp-vendor-*-session`) lets monitoring match every vendor activation.

Why the design looks like this (verified constraints, checked 2026-10-03 and 2026-10-04):

- **Without MFA trust, guests cannot be phishing-resistant.** B2B users then complete MFA in Contoso's tenant, where the only methods available are SMS, voice, Authenticator push, and software OATH tokens. With inbound MFA trust, home-tenant FIDO2, Windows Hello for Business, and certificate-based authentication are accepted. Hence trust, or Contoso-managed accounts.
- **Authentication strengths apply only to external users who authenticate with Entra ID.** Partners that sign in with email one-time passcodes or other federation get Contoso-managed member accounts or no access.
- **No CAE, no risk remediation for guests.** CAE does not support guest accounts, and guests cannot be risk-remediated in Contoso's tenant. Short sign-in frequency, narrow targets, and monitoring compensate.
- **Guest ZTNA is preview.** Microsoft's Known Limitations page titles its section on Global Secure Access for B2B guest users "B2B guest access (preview) limitations", so vendors use the broker rather than ZTNA (ADR-002).
- **PIM for Groups is assigned directly.** Assigning PIM for Groups eligibility inside access packages needs Microsoft Entra ID Governance or Microsoft Entra Suite. Microsoft's pages disagree on whether it is still in preview: the feature page and the licensing table carry no preview label, while a companion reference page links to the feature as preview. The status does not decide the matter. Base entitlement management features (access packages, approvals, expiry, external sponsors from connected organizations) are in Entra ID P2. Microsoft's guest licensing page bills a guest's access package request when the package contains a PIM group, through a separate monthly-active-user add-on with no free tier, so the design avoids depending on it.
- **No uncontrolled remote tools.** Remote access tools that vendors install themselves are removed from medical devices during onboarding review. Application control and egress filtering block unsanctioned remote access tools elsewhere.
- **Contracts carry the requirements.** The EHR vendor, the revenue-cycle outsourcer, and every biomedical vendor with broker access are business associates (`02-reference-architecture.md` section 11, A-13, A-14). Their engineers are their employers' workforce, not Contoso's: 45 CFR 160.103 defines workforce by the direct control of the covered entity or business associate they work for. The vendor model therefore maps to the business associate standards, not to the workforce specifications. Business associate agreements cover their HIPAA obligations (164.308(b)(1), 164.308(b)(3), 164.314(a)(1)). Section 164.308(b)(1) lets a business associate handle ePHI only after Contoso obtains satisfactory assurances, so a sponsor approves a partner's access package only when its agreement is on file. Contracts carry the security requirements (CSF GV.SC-05), and due diligence comes before access (GV.SC-06).

## 8. Patient identities

Patients and proxies sign in through `IDS-CIAM`, a customer identity tenant kept separate from the workforce tenant. Workforce Conditional Access, PIM, and B2B settings never apply to patients, and a compromise of a patient account cannot become a foothold in the workforce directory. Microsoft Entra External ID (external tenant) is one implementation. Azure AD B2C stopped being available for purchase by new customers on May 1, 2025. Portal MFA options and identity proofing are out of scope.

## Appendix: Entra role edge cases checked

### Device tag writers (planned lab test for section 3)

Supporting detail for the "Device tags" bullet in section 3 and note 10 under its policy table. "The same reference" below is Microsoft's reference for updating a device, which note 10 cites.

Where Microsoft's pages disagree. The same reference names Intune Administrator as the least privileged role for delegated calls, and says a user with Windows 365 Administrator "can only update basic device properties". Microsoft's default user permissions page lists only reading BitLocker recovery keys and disabling the device among the actions a device's registered owner can take, but its summary table says members can "manage all properties of owned devices". The design does not choose between these statements. The lab test: in a lab tenant, an account that holds only Intune Administrator sets `extensionAttribute1` on a test device through Microsoft Graph, as a control. Then an account that holds only Windows 365 Administrator, and an account with no role that is the test device's registered owner, each try the same call. With the control call accepted, two refused calls settle it. If the owner's call is accepted, the tag alone cannot mark a PAW, and CA-04 and CA-05 need a second device signal (ADR-004 Revisit when).

### Temporary Access Pass read permissions (planned lab test for section 4)

Supporting detail for the bullet "Applications that can issue a Temporary Access Pass are Tier 0" in section 4. "The same table" below is the permissions table in Microsoft's reference for creating a Temporary Access Pass, which that bullet cites.

Read permissions in the same table: for this call, the table (v1.0 and beta) also lists two read permissions as application permissions, UserAuthMethod-TAP.Read.All, marked least privileged, and UserAuthenticationMethod.Read.All. A read permission that creates a pass looks like a documentation defect, but the design does not assume it is one: an application holding either read permission is Tier 0 until a lab test shows it cannot create a pass. The test: in a lab tenant, an application granted only one of the two read permissions calls the create API for a test user, once for each permission. Two refused calls settle it.
